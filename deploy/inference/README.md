# Бортовая модель: развёртывание и история выбора

## Итог соревнования 29.09.2026

В рабочем сервисе используется Gemma 4 26B-A4B Q4_0 на мини-ПК
Ryzen 9 7940HS / Radeon 780M через llama.cpp. Unit
`mrbobus-inference.service` содержит фактический профиль запуска.
Отдельный benchmark генерации: около21,6 токена/с. Реальные текстовые
ответы модели использовались в миссиях; зрение модели не включено
в подтверждённый цикл распознавания QR (там ZBar/OpenCV).

Ниже сохранена история предварительного выбора кандидатов; её ранние
формулировки «не измерено» относятся к моменту выбора, а не к итогу.


Выбор предварительный до измерения на мини-ПК. Ничего из этого каталога
не запускает движение. LLM выбирает ID объекта из каталога; координаты,
доступность клетки и команды Nav2 определяет обычный код. Ответ `unknown`
или `ambiguous` не превращается в навигационную цель.

## Кандидаты (проверено по источникам 29.09.2026)

- Основной для первого измерения: **Qwen3.5-9B Q5_K_M**, text + vision.
  [Модель](https://huggingface.co/Qwen/Qwen3.5-9B),
  [GGUF](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF).
  Файл весов 6,578 GB, отдельный `mmproj-F16.gguf` 0,918 GB.
- Тяжёлый кандидат: **Qwen3.8-27B UD-Q5_K_M** — точное название реально
  существует, это не опечатка в названии Qwen3.5.
  [Модель](https://huggingface.co/Qwen/Qwen3.8-27B),
  [GGUF](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF).
  Веса 19,772 GB, `mmproj-F16.gguf` 0,928 GB. При 32 GB общей RAM
  дополнительно нужны память ОС, ROS, контекст и рабочие буферы; это
  кандидат для измерения, а не обещание приемлемой скорости.
- Альтернатива меньшего размера: **Gemma 4 E4B QAT Q4_0**,
  [официальный GGUF](https://huggingface.co/google/gemma-4-E4B-it-qat-q4_0-gguf).
  [Google](https://ai.google.dev/gemma/docs/core) указывает примерно
  4,5 GB базовой памяти; это не полная память процесса с контекстом.

Числа GGUF — десятичные GB размера файлов по Hugging Face API. Они не
равны RSS процесса или размеру VRAM. На нашем железе токены/с пока
не измерены. CPU и Vulkan/iGPU следует сравнить на одном запросе;
память встроенной GPU общая с RAM, не добавочная.

## Режим работы

Для первого развёртывания использовать `llama-server` из llama.cpp,
зафиксировать git revision сборки и revision/хеши скачанных моделей.
Начать с одного параллельного запроса, контекста 4096 (при необходимости
8192), отключённого thinking и ограниченного JSON-ответа. Не включать
автоматический запуск до проверки памяти одновременно с навигацией.
Модели и runtime хранить вне Git, например `~/robot/models` и
`~/robot/inference`; endpoint первоначально слушает только localhost.

На мини-ПК 29.09 подтверждены Ryzen 9 7940HS, Radeon 780M, 30 GiB RAM.
Собран llama.cpp `526c43b8f7dfea9032e9f35e7a1be9183ca7cc20`, CPU + Vulkan.
Пользователь добавлен в группу `render`; новая сессия нужна для доступа
к GPU (либо `sg render`). Обнаруженный бюджет Vulkan — около 16 GiB.
Установлен unit из этого каталога, **boot startup не включён**.

`download-model.sh` продолжает прерванные загрузки конкретной HF revision.
`verify_install.py` ждёт окончания загрузки, проверяет SHA256 из manifest,
измеряет CPU/Vulkan, запускает unit, выполняет миссионные и, при наличии
`vision-smoke.jpg`, один визуальный smoke test. Фоновый лог и результаты —
`~/robot/inference/verify-install.log`, `bench-ngl*.json`,
`mission-results.json`, `field-mission-results.json`, `vision-smoke-result.json`.
Наличие unit или файлов загрузки **не означает**, что модель прошла приёмку.
Каталог/фразы `field-*.json` — реальные ID разметки и придуманные проверочные
миссии; это не полученные задания соревнования.

LLM не должна анализировать каждый кадр видеопотока. На остановке передать
один кадр/кроп, получить короткое описание и наличие кандидата. QR искать
и читать обычным детектором/декодером; не принимать придуманный VLM текст
за прочитанный QR. VLM без геометрической проверки не задаёт координаты.

## Проверка

```sh
python3 tools/benchmark_mission_model.py \
  --url http://127.0.0.1:8088 --model robot-model \
  --output .local/inference/mission-results.json
```

Скрипт проверяет 8 **синтетических** русских заданий: прямое описание,
синонимы, отношение между объектами, отрицание, неоднозначность и
отсутствующий объект. Он сохраняет корректность, полное время запроса,
usage и timings сервера, если они доступны. Это smoke test, не оценка
качества на заданиях соревнования. Затем добавить реальные задания и
размеченные кадры с полигона: отдельно проверить пропуски пострадавшего
и ложные обнаружения на отрицательных кадрах.

Сравнивать время до готового JSON и результат, а не только decode tok/s.
Первый холодный запрос измерять отдельно от прогретых. Если 9B проходит
реальные примеры, 27B не нужна для управления. Если не проходит —
сравнить 27B на тех же примерах и принимать по качеству/задержке, а не
по популярности или размеру.
