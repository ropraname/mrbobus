## Привод

Два ODrive v3.6, fw0.5.6; CAN250k через MCP2515 12MHz. ID0 заднее правое+, ID1 заднее левое−, ID2 переднее левое−, ID3 переднее правое+. Hall72 CPR, радиус45mm, колея291.74mm, база215.5626mm. Циклические Encoder Estimates0x09 уже работают100Hz/ось, heartbeat10Hz; отдельный poll не нужен. Watchdog2s.

Принято предложение Тараса: стандартный `diff_drive_controller` → `odrive_ros2_control`, без standalone `odrive_node` и без новой самописной кинематики. Небольшая адаптация официального hardware-плагина лежит в `src/vendor` с MIT-лицензией и закреплённым upstream commit. Современный upstream не поддерживает3.x напрямую.

Реализованы velocity/position SI и знаки осей, legacy heartbeat, контроль свежести feedback, совместная остановка четырёх осей, CAN ошибки, блокировка единственного владельца CAN, lifecycle Idle и явное включение контроллера. Никакой фиктивной torque-телеметрии через0x1C (на0.5.6 это ADC). Отправка команд повторяется50Hz, пакеты разнесены на1.5ms для MCP2515. При Idle/повторном включении положение joint сохраняется: абсолютный estimator старой прошивки меняет начало отсчёта, его сброс не должен превращаться в перемещение базы.

`control.launch.py` запускает diff_drive_controller **inactive**. Стендовый профиль: команда колеса не более6rpm, линейная скорость до0.014m/s, ускорение0.007m/s²; предел тока **1A/ось**, только для вывешенных колёс. Настройки передаются в RAM при включении; flash не меняли. Старый robot_base при своём arm по-прежнему задаёт15A. Этот профиль не предназначен для езды по полу.

### Проверки

- 15 тестов исходной логики проходят. Стандартный mock на Pi: движение вперёд, поворот, остановка при потере команд — пройдены.
- `tools/test_odrive_control.py`, vcan0/domain43: настоящий controller_manager + новый hardware-плагин. Проверены направления, feedback-одометрия, повторение setpoint, timeout, inactive startup, deactivate/re-arm, all-axis stop при stale feedback и при axis error, отсутствие автоматического повторного arm. Найденная гонка lifecycle/read исправлена mutex. Финальный stale-тест также моделирует сброс абсолютных estimates между включениями.
- Реальный стенд: пользователь подтвердил вывешенные колёса и разрешил мягкие тесты. Команда0.007m/s (~1.5rpm), плавный разгон. Первые две попытки остановлены по мгновенному Hall velocity:13.5/16.7rpm; пользователь рывка не заметил. Во второй записи скачок совпал с одним шагом положения около1/72 оборота.
- Повтор с1A и контролем скорости по изменению позиции за0.5s:5s команды,2s нуля, затем deactivate. Все четыре оси откликнулись и завершили в Idle, ошибок осей0. Пики средней скорости3.80/4.92/4.93/4.01rpm; мгновенные оценки36–37.5rpm. Колёсная odom за тест +0.01077m — это вращение в воздухе, не перемещение робота.
- **Плавность и точность привода ещё не достигнуты:** при1A/1.5rpm движение ступенчатое, есть колебания положения, колёса проходят неодинаковый угол. Мгновенные Hall spikes нельзя считать доказательством такого же физического разгона, но нельзя объявить всё безобидным шумом. Нужны настройка и наблюдение под нагрузкой.

Данные диагностики вне Git: Mac `/tmp/mrbobus-audit/drive-samples-final.json`, Pi `/tmp/mrbobus-drive-samples.json`, `/tmp/mrbobus-control-real.log`. При следующем запуске временные файлы перезаписываются.

По архиву Тараса (не повторное чтение текущей RAM): encoder bandwidth100; старые оси0/1 vel_gain0.2, integrator1.0; новые2/3 gain0.106 после уменьшения вибрации, integrator0.333333. В архивном тесте12rpm мгновенная оценка оси1 доходила до−54/+34rpm при близкой средней скорости. Сохранённые параметры не менялись в этой работе; USB ODrive сейчас к Pi не подключены.

## Геометрия и LIO

Fusion MCP восстановлен, текущая `BOX_TANK_0.2_LIGHT` прочитана через API без изменения/сохранения модели. Четыре центра, радиус45mm и ширина55mm соответствуют существующему URDF. Нормаль площадки L2 и положение крепления совпали; геометрия корпуса уточнена. Источник размеров — `docs/geometry.json`. Поворот SDK вокруг нормали и фактическая сборка ещё требуют физической проверки; CAD не заменяет её.

L2: отдельный драйвер, IP192.168.1.62, Pi eth0 дополнительно192.168.1.2; cloud≈12Hz, IMU≈250Hz. Временные поля и внутренний IMU/LiDAR extrinsic проверены. Point-LIO портирован/собран на Jazzy, закреплён upstream; исправлены UB с индексированием vector после reserve и повторное накопление IMU при init. Подробнее и команды: [lio.md](lio.md).

Финальный живой тест60s:717поз/718облаков, задержка median17.8ms/max28.8ms, CPU25% одного ядра, RSS172MB. Отклонение положения до4.06cm на неподвижной базе после установления. Это подтверждает достаточность ресурсов Pi для стартового профиля, **не устойчивость при движении**.

Профиль15cm/каждая3-я точка существенно лучше плотного10cm/all. Плотный воспроизводимо расходится13.5m на одной стационарной записи даже после исправлений. Причина не доказана, перенос на Ryzen сам по себе её не устранит. Rosbag46MB сохранён вне Git на Pi. Выход пока отдельный `lio_odom→lio_imu`; владельцем `odom→base_link` остаётся колёсный контур, двойных TF нет. Повторная локализация по сохранённой карте/loop closure ещё не реализованы.

## Следующий практический шаг

1. Проверить/настроить низкоскоростную работу Hall-привода и достаточный ток под нагрузкой. Не повышать общий предел вслепую. Отдельно проверить поворот и физическое торможение.

3. Записать движение по известной траектории и возврат к старту; проверить LIO drift, внешний TF и covariance. Затем интеграция одометрии/карты. При необходимости вычислительную часть LIO перенести на мини-ПК, драйвер L2 может остаться на Pi.
4. После езды/локализации — препятствия, планирование, камера/QR/семантика и задание соревнования.
