# Unitree L2: LIO на Pi

Целевая платформа первого этапа — Pi 5 / 4 GB, Ubuntu 24.04 / ROS 2 Jazzy. Мини-ПК доступен как резерв; пользователь включил его после первых тестов. LIO использует существующие `/unilidar/cloud` и `/unilidar/imu`, второй драйвер не запускается.

## Источник и изменения

[ROS2 Point-LIO](https://github.com/dfloreaa/point_lio_ros2/tree/a8e2d0d5090af97ead8dd4fac3d37cf3dbb33ff7), commit `a8e2d0d5090af97ead8dd4fac3d37cf3dbb33ff7`. Upstream заявляет Humble; Jazzy проверяется нашей сборкой. Официальный [Unitree Point-LIO](https://github.com/unitreerobotics/point_lio_unilidar) использует ROS1.

Зависимость не копируется в Git проекта. `tools/setup_lio.sh` получает закреплённую ревизию без больших демонстрационных изображений и применяет `deploy/lio/patches/0001-bounded-queues-and-runtime.patch`: ограниченные DDS-очереди, SensorDataQoS IMU, постоянный executor вместо создания 5000 раз/с, цикл1000Hz, отключённое создание debug-файлов при выключенном логировании. В upstream обработчик Unitree игнорировал `point_filter_num`; патч применяет его. Также исправлены обращения по индексу к пустым `std::vector` после `reserve` (нужен `resize`) и повторное включение прежних IMU-отсчётов в среднее при инициализации (нужен `clear`, а не `shrink_to_fit`). Эти дефекты установлены чтением кода; они не объявляются доказанной единственной причиной дрейфа.

Профиль `src/mrbobus_lio/config/l2_pi.yaml`: voxel15cm, каждая третья точка, map cube100m / detection20m, без PCD/path/RViz, одометрия один раз на облако. Это стартовый профиль производительности; разрешение карты препятствий соревнования требуется оценивать отдельно.

## Проверенные входные данные

Живой пассивный замер 28.09.2026,10s:121cloud/2523IMU; обратных или одинаковых временных меток нет. Поле `time` float32 в секундах от начала облака, диапазон0…0.081257s; `ring` uint16. Cloud stamp отстаёт от получения примерно84.5ms, что соответствует началу накопления облака; IMU median0.42ms. Ускорение в m/s², среднее[-0.358,9.369,-3.444], поэтому `acc_norm:9.81`. Наклон датчика учитывается инициализацией gravity при неподвижном роботе, а не выдуманным поворотом входных данных.

Внутренний IMU/LiDAR extrinsic соответствует SDK: координаты начала LiDAR в IMU `[0.007698,0.014655,-0.00667]m`, R=I. Это не внешнее положение датчика на роботе. Параметр `extrinsic_T` используется в преобразовании `p_imu=R*p_lidar+T`.

## TF и ограничения

LIO публикует только отдельную ветвь `lio_odom→lio_imu` и `/lio/odometry`, зарегистрированное облако `/lio/cloud_registered`. Существующие `odom→base_link` и `base_link→unilidar_lidar→unilidar_imu` остаются у прежних владельцев. `lio_imu` — оценка позы IMU, не базы робота. До проверки движения, внешнего extrinsic и ковариаций не подключать эту одометрию непосредственно к Nav2/EKF. Upstream в обычном режиме оставляет covariance нулевой; это не подтверждённая нулевая неопределённость.

Point-LIO строит локальную карту и оценивает относительную позу; это ещё не повторная локализация в сохранённой карте и не loop closure.

## Установка и запуск

На новом хосте установить ROS2 Jazzy и `sudo apt-get install ros-jazzy-pcl-ros`, затем `tools/setup_lio.sh /home/USER/robot/lio_ws`. Исходники проекта должны оставаться доступны для symlink конфигурационного пакета.

На Pi рабочая отдельная сборка: `/home/taras/robot/lio_ws`. Рабочие сервисы не заменяются, автозапуск LIO не включён.

```bash
source /opt/ros/jazzy/setup.bash
source /home/taras/robot/lio_ws/install/setup.bash
export ROS_DOMAIN_ID=42 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file:///home/taras/robot/ros2_ws/deploy/cyclone-pi.xml
ros2 launch mrbobus_lio l2_lio.launch.py
```

При старте робот должен быть неподвижен для оценки gravity/bias. Остановить Ctrl-C. Пассивная проверка во втором терминале с тем же окружением: `python3 tools/check_lio.py --seconds 30`.

Для мини-ПК переносится этот пакет/профиль и закреплённая зависимость; драйвер L2 может остаться на Pi. Меняется CycloneDDS network config на интерфейсы нового хоста; абсолютных путей Pi внутри launch/config нет.
